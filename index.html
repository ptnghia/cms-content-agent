CMS Content Agent Pro

Install the WordPress plugin and self-hosted backend, then review proposed WooCommerce copy against live SKU and variation data before applying it.

Requirements

  • WordPress 6.2 or later and PHP 7.4 or later, as declared by the plugin. For the demo, use PHP 8.3 or later with SQLite extensions.
  • WooCommerce for products, SKUs, variation descriptions and catalog checks. The documented demo uses WordPress 7.1.5, WooCommerce 11.3.1 and PHP 8.4.
  • Administrator access to install the plugin and configure its backend. Reviewers need the capability to edit the target. A WooCommerce variation also requires permission to edit its parent.
  • Docker with the Compose plugin and an HTTPS hostname for the backend. The backend must reach WordPress over HTTPS, and the reviewer’s browser must reach the backend.
  • An Anthropic API key and access to a Messages API model for the deployment below. Provider usage is billed separately. The local WooCommerce demo runs without a backend account or API key.

Install and connect

1. Install the WordPress plugin

Back up WordPress and try the installation on staging. In WordPress, go to Plugins → Add New Plugin → Upload Plugin. Upload cms-content-agent-pro-plugin-0.7.0.zip, then activate CMS Content Agent Pro. Activate WooCommerce before copying backend configuration. For an existing Content Agent installation, WordPress will offer to replace the plugin in the same content-agent directory.

2. Configure the Docker backend

Extract cms-content-agent-pro-backend-0.7.0.zip on your server and open its backend directory. Copy the example environment file and create an empty site registry.

umask 077
cp .env.example .env
printf '{}\n' > config/sites.json
chmod 700 config

Set the following entries in .env. Replace the key and model placeholders with values from your Anthropic account. Keep the file private. These settings use the direct API backend and skip optional CLI downloads.

AGENT_BACKEND=api
INSTALL_CLAUDE=0
INSTALL_CODEX=0
ANTHROPIC_API_KEY=your-key
API_MODEL=your-messages-api-model-id
DEV_MODE=0

In the WordPress dashboard, open CMS Content Agent Pro → Settings. Enter the HTTPS address for the backend, save, then copy the Backend configuration JSON to config/sites.json. Merge the site entry into the object when connecting an additional site. Compose mounts the JSON read-only. On a standard Linux host, grant the container process permission to read the mounted file while keeping the host directory private. Then build and start the service.

chmod 644 config/sites.json
docker compose config --quiet
docker compose up --build -d agent
curl -fsS http://127.0.0.1:3000/api/health

Run the health check on the Docker host. In production, keep port 3000 bound to loopback and forward traffic through a reverse proxy on HTTPS with a valid certificate. Pass Server-Sent Events without buffering and set a read timeout long enough to finish a chat request. An example location block for an existing TLS-enabled nginx virtual host follows.

location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_read_timeout 600s;
}

3. Verify the connection

Reload the plugin’s Settings page and verify that the backend is reachable. Open the chat widget and run a site sync. On a staging catalog, ask the assistant to propose a description for a known variation SKU and include the exact variation ID. Open CMS Content Agent Pro → Proposals to review the queued result.

Review a product proposal

  1. Open a pending proposal. The page shows the target, WooCommerce catalog evidence, findings and a before-and-after diff.
  2. Compare the stated SKU and facts with the variation ID, selected attributes and current prices. Check claims marked Verify with the product team or manufacturer.
  3. If Apply is blocked, reject the proposal with a reason and ask for corrected copy. If the evidence supports the draft and Apply is available, choose Apply changes.
  4. Check the product page or variation in WooCommerce. You can open the applied proposal and choose Revert to previous version to restore the saved description. Check for newer edits before reverting.

For a variation, the proposal targets the exact WooCommerce variation ID and updates its description using WooCommerce’s product API. The store continues to use WooCommerce fields for SKU, price, stock and variation attributes.

Supported copy checks

CopyCatalog comparison
SKUUse an explicit label such as SKU: TRAIL-750. An exact match is case-insensitive. A different SKU blocks a direct proposal when the target has its own SKU.
CapacityRecognizes English mL and L quantities. A single clear quantity is compared with a single value in a Capacity or Volume attribute. 0.75 L and 750 mL are equivalent. Ranges and accessory contexts need review.
PriceFor direct figures, use English-style decimals and an ISO currency code such as USD 29.00. Use regular price or sale price immediately before the amount to compare against those fields. The default comparator is WooCommerce’s stored current price. Tax, shipping, conversion, contextual pricing and multi-currency display prices need manual review.
Care and performanceSome English claims, including leakproof, dishwasher-safe and selected hot or cold duration phrases, trigger a manual evidence check.

For shared copy on a variable product, put exactly one active variation SKU and its claim in the same sentence, for example SKU: TRAIL-750, 750 mL for USD 29.00. Unscoped claims need manual verification. A wildcard attribute or missing structured fact can also require verification.

The check scans proposed long and short descriptions, SEO titles and meta descriptions. It checks the resolved field when a proposal uses a patch and runs again on Apply. If the target SKU or variation selection changed since a new proposal was queued, create a fresh proposal for the updated target. The parent evidence reads up to 100 child records, while a direct variation proposal reads the exact variant. The scanner reports its coverage limits. It recognizes specific English patterns, so review surrounding context and other product claims before publishing.

Data and maintenance

WordPress generates an API key and a token secret when the plugin is activated. Restrict access to those values and the provider key. The backend syncs enabled site content, catalog data and proposal status into its site workspace. When you use a provider-backed feature, the backend sends the prompt and relevant context to the configured provider. Review each provider’s processing and retention settings before sending customer material.

Back up the WordPress database, private backend config and agent-data Docker volume before updates. Leave DEV_MODE=0 on hosted deployments. If rotating WordPress keys, replace the matching site entry in config/sites.json and restart the service using docker compose restart agent. Deactivation and uninstall preserve proposals and settings by default. To delete those records on uninstall, set CONTENT_AGENT_DELETE_DATA_ON_UNINSTALL to true in wp-config.php before deleting the plugin. Applied product copy and existing SEO metadata remain in WordPress.

Troubleshooting

  • Backend unreachable. Check docker compose logs agent, the local health endpoint, DNS, TLS and browser access to the configured backend URL.
  • WordPress sync returns 401 or 403. Verify the site API key, the content-agent/v1 endpoint, and forwarding of the Authorization header through WordPress’s proxy. Check that your security plugin allows the authorized backend request.
  • Backend works but chat fails. Verify the API key, provider account, selected model and request limits. Open logs on the backend host.
  • A variation is missing. Confirm WooCommerce is active, activate the variation, run site sync again and check whether the parent exceeded the 100-child evidence limit.
  • Apply is blocked. Check the most recent catalog data and patch context, then queue a corrected proposal. A review warning can be cleared by verifying the claim editorially before applying.
